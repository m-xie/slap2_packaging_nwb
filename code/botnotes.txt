IMPLEMENTED SYNCHRONIZATION BEHAVIOR
------------------------------------
HARP signals:

  DO0 = SLAP2 acquisition/trial start
  DO1 = SLAP2 acquisition/trial end
  DO2 = legacy P3 stimulus onset
  DI3 = primary-plane SLAP2 cycle clock
  AnalogInput0 = physical photodiode

Stimulus timing:

1. Legacy P3 behavior is preserved: when DO2 count equals stimulus-table row
   count, DO2 timestamps remain authoritative.
2. When DO2 is empty, logger stimulus times are mapped onto HARP time by an
   affine fit to expected logger photodiode transitions and measured HARP
   AnalogInput0 transitions.
3. A nonempty but mismatched DO2 signal raises instead of silently falling back.
4. Logger selection is deterministic: prefer a filename containing "dup";
   otherwise use the first sorted logger path.
5. Logger/HARP fit metadata is printed as "stimulus timing" and records source,
   logger path, transition counts, frame rate, and residual statistics.

Maedeh continuous acquisition handling:

1. Source extraction can split one physical acquisition into many processing
   chunks. These are collapsed only for synchronization; chunk frame counts are
   retained separately.
2. Continuous mode is inferred conservatively from one HARP DO0/DO1 pair, one
   raw trial ID, cycle-chunked .dat files, and continuing line indices.
3. A partial first extracted chunk may start at a positive line index other than
   1. This is valid for continuous mode.
4. Parsed DI3 rising edges before the first retained DO0 are removed before
   cycle assignment. Do not remove or replace the historical gap-detection and
   line-count reconciliation logic.
5. Pre-bug-fix P3 sessions still use trial gap detection. Exact DI3/raw cycle
   equality is not required; historical warning/clamping behavior is preserved.

Chunked .dat support lives in slap2_dat_utils.py. TRIAL is the logical trial;
CYCLE is a zero-based chunk offset, not a cycle count. Chunk continuity must
satisfy:

  next offset = current offset + cycles in current file

Do not move parsing/validation back into run_capsule.py.

OPEN ZEBRA CORRELATION INVESTIGATION
------------------------------------
The user noticed that almost all per-ROI Zebra repeat correlations are near zero
and considers this suspicious. No modification has yet been made for this issue.

Current calculation in zebra_movie_qc.py:

1. Find the Zebra movie interval.
2. Treat one 600 s interval as two consecutive 300 s repeats, or use two equal
   explicit intervals.
3. Bin dF/F into 100 ms bins.
4. For each ROI, compute Pearson r between matching bins in repeat 1 and repeat 2.
5. "Global r" flattens all ROI/time values. It can be inflated by stable
   between-ROI baseline/variance differences and is less informative than the
   median per-ROI r for temporal reliability.

Observed global r / median per-ROI r:

Interpretation so far: r near zero means the temporal dF/F pattern does not recur
at the same 100 ms movie bins. It does not mean zero activity. Overlaid traces
look dominated by irregular transients. Both green and red being low suggests
non-repeat-locked activity, noise, motion/hemodynamics, baseline drift, or an
alignment issue rather than clearly reproducible movie responses.

Most useful next checks, in order:

1. Verify that both 300 s windows contain the same movie frames and that the
   interval split is correct. Do not assume a 600 s Zebra block is exactly two
   identical frame sequences without checking logger/frame events.
2. Quantify per-ROI correlations at coarser bins or after smoothing (0.5, 1, and
   2 s). This tests whether 100 ms resolution is too strict for calcium dynamics.
3. Compute lagged correlation over a small shared lag range. First estimate one
   session/repeat offset from a population trace; do not optimize a separate lag
   per ROI because that will inflate reliability.
4. Compare raw dF/F, detrended/high-pass traces, and optionally neuropil/motion
   regressions. Use the same transform for both repeats.
5. Add uncertainty/null estimates, e.g. circularly shifted repeats or unrelated
   windows. With only two repeats, r alone is a weak reliability estimate.
6. Check known orientation/RF-responsive ROIs as positive controls. If those are
   reliable but Zebra is not, a biological/stimulus-specific interpretation is
   more plausible.

Changes that may legitimately improve sensitivity: modest smoothing/coarser
bins, one independently estimated shared lag correction, consistent detrending,
and verified frame-level repeat boundaries. Avoid cherry-picking per-ROI lags,
dropping low-r ROIs, or smoothing until r rises; those merely inflate the metric.
